# Azkarapp app review and Android release readiness — 15 October 2026

## Objective

Review the current application, screen families, maintainability, tests, offline behavior, deployment evidence and Google Play readiness. Research established devotional-app widget patterns and deliver at most four widget concepts as images.

**Verdict:** the web application has a strong working foundation, but it is not yet a verified Google Play release candidate. Two existing product defects were reproduced despite a passing normal quality gate. Android packaging, native lifecycle behavior and physical-device acceptance still need a separate approved phase.

This is an audit and concept phase. No application code, reviewed content, state schema, dependency, CI assertion or production configuration was changed. Findings distinguish reproduced defects, source-confirmed gaps, recommendations and unverified device behavior. This review covers every consumer screen family found in the repository; it does not claim every religious passage, all 604 pages, every account state or every device combination was manually reviewed.

## Scope completed

- Read the repository architecture, design, content, quality, current phase/decision and relevant prayer, audio, motion, synchronization and design-coverage contracts.
- Inspected source ownership, route inventory, persistence, account/device sync, legal pages, dependency policy and release workflows.
- Captured the actual application in the Codex in-app browser at phone, tablet and desktop widths. Arabic Midnight is the main screen inventory; English, Light and Dark have supplementary captures. Automated tests additionally cover 320px and enlarged text.
- Used an isolated localhost origin for counting, language and theme changes. Production smoke used the deployed origin separately.
- Ran full non-browser quality, 51 existing Chromium browser checks, one focused WebKit reproduction, dependency audit, English-content coverage and complete browser inventory verification.
- Inspected exact-commit CI job outcomes and logs instead of treating a green badge as proof of no flakes.
- Created isolated diagnostic tests under the ignored evidence directory. Their failures intentionally preserve proof of existing defects; they are not hidden failures of the normal suite.

## Highest-priority findings

### A01 — P1: first-time completion can navigate away instead of showing the summary

**Reproduced, high confidence.** Counting all four Home azkar returned to Home. The completion presentation itself renders when opened directly, so the failure is in the transition rather than its layout.

`getEffectiveCompletedForSubcategory` returns the original set for ordinary categories (`src/app/progress.ts:608`). `markComplete` adds directly to that set (`src/app/hooks/useSessionHandlers.ts:255`). A delayed `advanceAfterCompletion` callback then sees the old snapshot as already complete and calls `pop()` at lines 361–364. This also violates React state immutability. Similar optimistic `.add`/`.delete` uses should be inspected together.

The isolated reproduction uses the existing session test harness and captures the advance callback before the final count, matching the counter timer. Both assertions fail: the previous set changes, and `pop` is called instead of reaching completion.

**Repair:** derive an independent optimistic set; preserve the distinction between a newly completed session and revisiting an already completed collection. Do not change completion IDs, merge rules or reviewed counts.

**Acceptance:** prior state remains unchanged; a first final count reaches the summary exactly once; repeat, already-complete, reset-during-delay, shared-mode and per-prayer flows remain correct. Add a real browser test from an incomplete collection through its final count, rather than testing the summary route alone.

Evidence: `46-home-after-counting-ar.png`, `49-completion-preview-en.png`, `completion-reproduction.test.tsx`, `reproduction-results.json` in the local evidence folder. The direct preview is explicitly not proof of a successful normal transition or an accurate session duration.

### A02 — P1: Account & data crashes if browser storage access throws

**Reproduced, high confidence.** `AccountDataPanel.tsx:62` reads `window.localStorage` in a state initializer without a guard; line 81 repeats it in the event handler. Optional chaining does not catch a throwing storage getter or `getItem` call. A simulated `SecurityError` causes rendering to throw, even though the rest of the app has storage-recovery boundaries.

**Repair:** consume the existing guarded device-status boundary or a dedicated hook, and show a local-storage limitation without losing export/recovery controls. This also removes storage ownership from presentation.

**Acceptance:** mount, focus and device-change events remain safe with blocked getters, failing reads and failing writes. Existing saved state must not be erased to recover.

Evidence: `storage-reproduction.test.tsx` and `reproduction-results.json`.

### A03 — P1 before store submission: privacy descriptions differ from current processing

**Source-confirmed.** A public privacy policy and external account-deletion page already exist; this is not a missing-page finding.

- The in-app Legal summary describes optional Supabase processing but omits anonymous Cloudflare pairing and visitor processing.
- `public/privacy.html` describes a short-lived fingerprint and only a first-seen time. The client actually creates a persistent random visitor ID in local storage, sends it while visible every 30 seconds, and the Worker stores both first-seen and last-seen timestamps. The Worker has a 24-hour inactive-visitor retention cleanup policy. Actual deployed cleanup execution and private secret configuration were not independently verified.
- The policy says unlinking is through support or clearing a local credential; an in-app unlink action now exists. Unlinking one device, removing local data and deleting all remote account data are different operations.
- The account-deletion handler calls Supabase deletion. Cloudflare paired-device data has its own ownership and retention lifecycle and must be explained independently.

**Repair:** create one reviewed bilingual data-processing inventory and use it for the public policy, in-app summary, deletion documentation and Play Data safety answers. Cover identifiers, prayer/practice history, optional account identity, network providers, downloads, retention and deletion scope. Assess Google's religious-belief data category against the actual synchronized fields; do not automatically declare that no data is collected because the app works offline.

**Acceptance:** disclosures match verified requests and storage for guest, paired-device and signed-in modes; each deletion path states exactly what it removes and retains. Existing [public policy](https://amahdy59.github.io/Azkarapp/privacy.html) and [deletion page](https://amahdy59.github.io/Azkarapp/account-deletion.html) remain publicly reachable. Policy reference: [Google Play Data safety guidance](https://support.google.com/googleplay/android-developer/answer/10787469?hl=en).

### A04 — P1 reliability risk: QR/device requests have no application deadline

**Source-confirmed risk, not a measured production outage.** `src/lib/cloudflareSync.ts` calls `fetch` without a deadline/abort boundary. A request that never settles can leave pairing controls pending indefinitely and keep `useCloudflareDeviceSync` busy, preventing its bounded retry logic from starting. Visitor heartbeat requests can overlap when one takes longer than 30 seconds.

**Repair:** a shared bounded request service, cancellation on lifecycle changes, one in-flight visitor request, offline gating and appropriate backoff. Expose Cloudflare sync state instead of silently exhausting retries. Keep local reading and progress independent.

**Acceptance:** never-settling fetch, disconnect, 401, 409, 429, reconnect and unmount recover predictably without duplicate writes or secret-bearing error text.

### A05 — P1 release evidence gap: recording redistribution permissions

**Source-confirmed documentation gap, not a claim of infringement.** `AUDIO_SOURCES['internal-upload']` has `licenseName: 'Publicly distributed'` and `licenseEvidence: 'N/A'`. That source is referenced by recording variants. The repository's own audio contract explicitly says public availability is insufficient evidence for hosting, offline caching and redistribution.

**Action:** retain durable permission evidence for every recording actually shipped, including download/ZIP redistribution. Verify owner-upload permissions, Quran fonts, translations and supplied artwork in the same release asset register. Do not invent licenses or remove attribution as a shortcut. Private permission documents may already exist; they were not available in this audit.

## Android / Google Play readiness

### What exists already

React/TypeScript/Vite PWA; web manifest, service-worker offline reading, validated persistence, local prayer calculation, optional account/device sync, public privacy/terms/deletion pages, strict quality and exact-main deployment gates. These are worth retaining.

### What is not present or verified

No Android Gradle project, Capacitor configuration, Bubblewrap/TWA project, AndroidManifest, native AppWidgetProvider, signed AAB or native release workflow was found in the tracked application. The current web manifest does not create Android home-screen widgets. Play Console setup/account eligibility, signing ownership and listing declarations were not inspected.

**Recommended architectural decision:** for this product's desired widgets and dependable local prayer reminders, evaluate a thin Capacitor Android host with native widgets and scheduling services, while retaining the existing React application. A TWA is a valid web-first store route, but does not by itself solve widget data sharing or native local scheduling. This is a recommendation for a separate approved dependency/platform phase, not an implementation or approval assumed by this audit. Sources: [Capacitor](https://capacitorjs.com/), [Trusted Web Activities](https://developer.chrome.com/docs/android/trusted-web-activity).

## Widget research and four recommended concepts

These are native Android launcher-widget concepts, not extra in-app cards. Images are generated proposals grounded in the current app's screenshots and official competitor documentation. Competitor apps were not installed or benchmarked; documentation/screenshots establish patterns, not comparative performance or a market-share ranking.

- [Muslim Pro Android widget documentation](https://helpdesk.muslimpro.com/help/en/articles/homescreen-updated-widget-android) documents prayer times/tracking, Quran continuation, duas and interactive tasbih. Adopt focused access and continuation; avoid copying ad-unlock friction or making a widget a second crowded dashboard.
- [Pillars](https://www.thepillarsapp.com/) emphasizes simple prayer widgets and location privacy. Its [FAQ](https://www.thepillarsapp.com/faqs) documents stale widget values after location changes and the distinction between today's and tomorrow's Fajr. Treat those as explicit correctness cases.
- [Greentech Apps Foundation](https://gtaf.org/blog/gtaf-q4-2024-highlights/) documents a hadith home-screen widget; [Quran Android](https://android.quran.com/) emphasizes bookmarks, translations and verse-highlighted audio. These support restrained content/continuation patterns; they are not evidence that Quran Android offers the proposed native widget.

| Priority | Widget                   | Suggested size                    | Behavior / why                                                                                                                                                                                                                                                                         |
| -------- | ------------------------ | --------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1        | Prayer times             | 4×2, with a later compact variant | Next prayer and exact time dominate; five prayer times below; selected city and valid date. A tap opens the exact prayer screen. No direct religious-practice recording in v1.                                                                                                         |
| 2        | Daily azkar continuation | 4×2                               | Current routine, factual completed-item count and one Continue action to the first incomplete item. Secondary evening/sleep links only when there is space. Use saved core/complete context and the same practice-day rules as the app.                                                |
| 3        | Quran continuation       | 4×2                               | Exact last saved page/surah/juz, independent daily reading count and Continue. Offline badge only when the required content/fonts are verified cached. Opening a widget never marks reading complete.                                                                                  |
| 4        | Tasbih counter           | 2×2, optional second release      | One large local increment action, factual count and explicit app-open action. Reset/formula changes occur inside the app. Ship after the native state bridge proves no lost/duplicated taps or conflict with app counts. A target is user-selected, not a claim of a prescribed count. |

The recommended first widget release is 1–3. The counter is useful but carries greater write/race risk. Qibla is a better deep link than a continuously active compass widget; it avoids implying live sensor correctness from a static launcher surface.

### Widget implementation contract

- Use native Android widgets, for example [Jetpack Glance](https://developer.android.com/develop/ui/compose/glance), with a versioned local presentation snapshot derived from normalized app state. Do not introduce a second interpretation of prayer formulas, Quran position or completion semantics.
- Native code cannot simply read the website's localStorage. Define a narrow app/native bridge and durable device-local store. Read-only snapshots first; mutation commands require stable IDs, atomic/idempotent handling, acknowledgements and reconciliation when the web app resumes.
- Precompute a bounded prayer schedule from the existing calculation contract, settings revision, coordinates/timezone and adjustments. Invalidate on date, timezone, location, method and adjustment changes. Label tomorrow's Fajr explicitly and mark expired/unavailable data instead of presenting stale times as current.
- Do not depend on a JavaScript interval or one-second background polling. Android's ordinary `updatePeriodMillis` is not a precise prayer scheduler and has a 30-minute minimum. Use event updates and platform-appropriate scheduling; use native timestamp/countdown presentation where supported. [Android widget update guidance](https://developer.android.com/develop/ui/views/appwidgets/advanced).
- Test multiple widget instances and sizes, launcher resize, restart/reboot, process death, app upgrade, denied permissions, zero data, stale data, offline use, midnight and practice-day rollover, two rapid taps and simultaneous app/widget counting.
- RTL text/order and right-origin progress, localized isolated numbers, at least 48dp native actions, readable text on opaque surfaces, TalkBack labels and font scaling. The concept boards are visual direction; native implementation must measure targets rather than infer them from pixels in an image.
- Never regenerate devotional text through an image model for shipping. Bind approved repository content and source identities. The supplied concepts deliberately avoid verse bodies.

Four final boards live in `output/app-audit-2026-10-15/widgets/`, each with light/dark examples of the same widget family. Times/progress are illustrative, not a current Cairo timetable. The final prompt set and image-generation method are recorded in `WIDGET_BRIEF.md` in that folder.
