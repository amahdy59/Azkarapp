# Phase Report — Home prayer cards, tracking dialog and manual disclosure

## Objective

Apply the owner's approved prayer-layout recommendations locally: desktop-style tablet timers, a deliberate tracking overlay, dated recorded checks, explicit Show/Hide within Now/Next, and consistent scroll elevation. Publication remains on hold.

## Scope completed

- Timer anatomy follows the available container width. At 768px the five cards use the desktop icon/name/time/status structure; narrower and enlarged layouts reflow without removing prayers or shrinking text.
- Recorded status derives from the existing normalized record for the supplied prayer/day. Both home and mosque records count; independently completed adhkar/Sunnah do not imply attendance. Undo and reload retain the correct result.
- An eligible native card button opens one protected responsive tracking overlay. Desktop retains complete reviewed evidence in two columns; compact guidance uses native disclosures inside the same overlay. There is no nested information modal.
- The labelled Show/Hide button controls the timing grid and location. Dates and Now/Next remain available. Scroll, clock rollover, resize and dialog dismissal preserve the reader's transient choice. Location acquisition/result recovery retains its opener.
- Home uses the existing ordinary-page scroll-elevation hook, threshold hysteresis and reading tint. The old automatic-fold hook, duplicate compact copy and fold-space reservation are removed. Explicit disclosure has one finite transition with app/OS still alternatives.
- Screenshot review found cramped Arabic labels at 320px/200% text. Capping decorative inset/gap growth restores whole-word reading room while preserving enlarged type and 44px targets.

## Components added or modified

`HomePrayerSummary` owns the persistent Now/Next presentation and native disclosure action. `HomePrayerOverview` owns the five cards and dated saved-state presentation. New `PrayerTrackingDialog` composes the existing protected `ResponsiveSheet`, header, `PrayerMomentPanel`, autosave explanation and shared Done button. `PrayerActionsCard` supports compact guidance in that overlay while retaining the existing desktop columns. Screen-owned state and App-owned persistence remain upstream of reusable presentation.

## User-visible changes

Prayer cards have readable times, clear current/next status, recorded icon plus text and a distinct opened-card outline. Activating a prayer keeps Home's content geometry intact. Changes save immediately through the existing path; Done closes the overlay. Read stays independent from checking an action. Hide removes timing/location controls from keyboard and accessibility navigation until Show is activated. The clock never opens a modal automatically.

The disclosure choice lasts for the mounted Home screen; it is not a new persisted preference. Existing prayer opening/recording windows, exact day keys, midnight/DST, calendar and Friday naming remain authoritative.

## Accessibility work

- Native buttons, checkboxes and details; labelled dialog/close/Done; protected opaque functional surfaces, bounded scrolling and focus containment/return.
- Current/next, selection and recorded state use text/semantics rather than color alone. Timers remain passive rather than recurring live announcements.
- Restored the prayer group's level-two heading after splitting the persistent summary from the five level-three cards. The dialog supplies its own heading without duplicate internal headings.
- Geometry/hit-target, 320px/200%, responsive portal replacement, keyboard disclosure/Escape, independent Read, reduced motion/transparency, high contrast/forced colors and axe regressions remain in the affected tests.
- Native Android Back uses the shared overlay stack. Browser Back retains existing route navigation. Physical Android/iOS and human screen-reader checks are still separate acceptance work.

## Tests added or updated

The new dialog spec checks dated recorded state, unrelated-deed independence, undo/reload, recording eligibility, focus recovery, explicit disclosure across scroll/clock/resize, five responsive widths and both languages/material families. Each viewport has an independent case so WebKit completes the same assertions within the unchanged deadline. The narrow cases check at least 100px of label reading width, in addition to visible Close/Done/Read and no page overflow.

Existing suites replace obsolete inline-panel, nested-info and automatic-fold expectations with the approved observable behavior. Source text/count/reference, persistence, calendar, theme/fallback, geometry, keyboard, timing and reader assertions are retained. No skips, coverage reductions, dependency changes or budget increases were introduced.
