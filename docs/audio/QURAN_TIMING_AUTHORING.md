# Reviewed Quran listening annotations

Phase 88 adds a review-ready system, not timestamps for the current reciters. `QURAN_TIMING_CATALOG` in `src/app/audio/quranTimings.ts` deliberately ships empty. The UI explains that following is unavailable and allows manual page browsing.

## Preparing an annotation

1. Select an approved variant in the audio manifest. Record its exact `variantId`, SHA-256, duration and segment Quran range. Never transfer alignment between reciters, edited files or differently encoded recordings.
2. Listen to that exact file and annotate complete, ordered verse intervals in integer milliseconds. Use end-exclusive intervals. Leave real gaps unannotated; do not stretch a word through silence. Media `currentTime` already accounts for playback rate.
3. Optionally annotate every semantic word position of a verse, using the shipped `public/data/mushaf` tuples as identities. Do not include end-marker glyphs as words. Word intervals must be ordered and contained in the parent verse. Omitting all words keeps verse following available without claiming word alignment.
4. Record the source/evidence, author, a different human reviewer and the review date. The reviewer must listen at normal and slower speeds, inspect all verse boundaries, words, long pauses, opening basmalah, seeking and the final verse. Automated transcripts may assist drafting; structural validation cannot approve religious/audio alignment.
5. Register the reviewed annotation in `QURAN_TIMING_CATALOG`. Required fields are `variantId`, `sha256`, `durationMs`, `unit: "milliseconds"`, `source`, `authoredBy`, `reviewedBy`, `reviewedAt` (YYYY-MM-DD), `reviewStatus: "approved"`, and `verses`. Each verse has `verseKey`, `startMs`, `endMs`, and optional `words`; each word has `position`, `startMs`, `endMs`.
6. Run `node scripts/validate-quran-timings.mjs` and `pnpm check`. The authoring check compares approved recording identity and duration, complete verse coverage, interval order and the actual shipped semantic word positions. Runtime also rejects a missing, duplicate, unreviewed or mismatched annotation.
7. Add browser evidence for that recording before release: optional word emphasis, following after seeking/repetition, manual browsing and return, source changes, narrow screens, keyboard operation and reduced motion. No runtime credentials or alignment network service are introduced.

## Presentation boundaries

The expanded player lazy-loads a read-only version of the shared Mushaf canvas for Baqarah, Kahf, Sajdah and Mulk. It loads only the displayed page, settles the matching QCF font with the existing bounded Unicode fallback, and does not update reading progress or bookmarks. Full printed pages may include adjacent-surah text, as the Mushaf does. Unicode Quran passages use Amiri Quran independently of the reader's ordinary zikr font. Compact 44px page arrows, a short page label and an information button preserve the reading area. Unavailable-following guidance opens on demand in an accessible popover; no inactive Follow button takes space. The toolbar meets the viewport's top edge so scrolled text cannot appear above it.

On opening, the selected surah's printed heading (or first verse when the heading is on the preceding page) is brought into view if it lies below the listening viewport, notably Al-Kahf on page 293. This is structural page navigation, not inferred audio synchronization. Page controls remain sticky while reading; the paper honors the Mushaf theme and scale. A margin marker identifies active verse lines without relying on color, including when an ayah continues onto another page. Keyboard scrolling also pauses following. If page data is unavailable, the existing reviewed page-boundary splitter displays the original text in Amiri Quran without rewriting it; retry restores the page layout when connected. Error announcements do not make the Quran text a live region. Semantic Arabic spans declare their language independently of English interface labels.

Following starts off. With reviewed timings, verse emphasis is quiet, optional words have an underline/outline as well as color, and automatic movement uses instant scrolling without focus changes. Page browsing, wheel or touch scrolling pauses following; the Follow control returns to the current verse. Verse text remains available to assistive technology with a quiet `aria-current` marker. No word-by-word live announcements are emitted. The media clock samples only while playing and visible and renders only when the active cue changes. Collapsing the player never restarts audio; browsing state currently resets when the expanded view remounts.

## Efficient timestamp drafting (owner follow-up, 2026-10-08)

First check an existing annotation catalog against the exact recording, not just a reciter's name. [Quran Foundation's audio SDK](https://api-docs.quran.foundation/docs/sdk/javascript/audio/) exposes chapter timestamps and word segments. [QUD Universal Audio v3.2.0](https://github.com/QUD-Technologies/quranic-universal-audio/releases/tag/v3.2.0) publishes audio source metadata alongside annotations for 69 recitations. Its downloaded catalog was inspected: neither Muhammad Al-Shara / محمد شرعي nor Abdullah Muhammad / عبد الله محمد is listed. This is a catalog check, not proof that no annotations exist anywhere. No matching annotation was found or imported, and no different reciter or encoding is substituted.

For the existing recordings, use forced alignment of the known Quran transcript rather than first transcribing it and accepting recognition errors. [CTC Forced Aligner](https://github.com/MahmoudAshraf97/ctc-forced-aligner) accepts supplied text and audio; [WhisperX](https://github.com/m-bain/whisperX) provides a separate language-specific alignment stage. These are offline authoring options, not app dependencies. Arabic/tajwid, repetitions and unspoken tokens can defeat an aligner; interpolated or unmatched words must be marked for review rather than assigned plausible-looking times.

Preparation evidence is in `output/quran-alignment-preparation/`: manifest-bound JSON with untouched Unicode word text, verse keys and semantic positions, plus verse-per-line transcripts. Counts checked against the shipped Mushaf are Baqarah 286 verses / 6,116 words, Kahf 110 / 1,579, Sajdah 30 / 372 and Mulk 30 / 333. These files contain no invented timestamps and are not loaded by the app. The public catalog snapshot is `output/qud-catalog-v3.2.0.json`.

Start with Mulk (429,264ms) before Sajdah (527,640ms), Kahf (1,931,376ms) and Baqarah (6,825,000ms). Verify downloaded original bytes against the manifest SHA before alignment. Decode to a working mono PCM copy without trimming or changing the original playback timeline. Inspect any codec lead-in offset against native-player playback. Keep the original audio and digest as annotation identity.

Draft verse anchors first, then align words within reviewed verse windows. Long Baqarah should use overlapping, verse-bounded batches and stable anchors; never divide its duration evenly among verses or words. An opening basmalah or other spoken material outside the selected semantic verse range stays an explicit unannotated interval. Review repetitions, silence, low-confidence/unmatched tokens, zero-length words, skipped verses and batch seams. Reconcile aligner tokens to the untouched semantic word map, not to QCF glyphs; font rendering remains independent of timing data.

The current machine has an Intel Iris Xe GPU and no installed Torch/alignment stack or FFmpeg executable. Preparation and catalog checks were completed; model inference was not run. Use one isolated authoring environment and cache one Arabic model, preferably on a suitable GPU for the long recordings. No runtime dependency, upload service or credential is needed in the application. Save drafts separately with an unreviewed status; after the independent listening review above, validate and release verse cues first, then words. Phrase boundaries require their own reviewed grouping and are not inferred from pauses alone.
