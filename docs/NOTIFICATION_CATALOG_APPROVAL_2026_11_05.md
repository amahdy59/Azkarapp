## 2. Linking problems to approve fixing first

1. Browser notification URLs currently interpolate raw category IDs such as `after_prayer`, `before_sleep` and `comprehensive_duas`; the router expects `after-prayer`, `before-sleep` and `comprehensive-duas`. Native scheduling already uses hyphenated slugs. Use the shared route builder for both paths.
2. Browser notification `data.url` is populated, but source and generated-worker inspection found no explicit `notificationclick` handler or constructor-notification click navigation. A URL in notification data alone does not open it. Approve worker click handling plus constructor fallback, with same-origin route validation, existing-client focus and cold-start behavior. [MDN notificationclick documentation](https://developer.mozilla.org/en-US/docs/Web/API/ServiceWorkerGlobalScope/notificationclick_event).
3. Android already handles `localNotificationActionPerformed` and reads its route. Preserve that behavior and verify foreground/background/cold-start delivery on device.
4. The current URL model supports collection/index routes, not a permanent zikr-ID route. The links above open real sections. For a precise featured zikr, approve a stable-ID resolution mechanism; do not publish guessed indexes or an ignored query parameter. Until then, open the matching collection and keep the zikr name visible in the notification.
5. “Open evidence” for a notification's full hadith needs an explicit source-detail flow. Existing Home reading data may supply content, but an arbitrary notification-source route does not yet exist. No invented `/reminders/...`, donation, Duha or fasting-calendar URL is presented as working here.

## 4. Rotation behavior — a separate approval decision

| Rule                     | Proposal                                                                                                                                                                                                                                                                      |
| ------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Stable selection         | Derive a deterministic sequence from the dated scheduled occurrence and reminder type. Reopening, rerendering, updating settings or rebuilding Android's queue must not choose a different quotation for the same event. No runtime text generation or network source lookup. |
| Independent pools        | Rotate within each prayer/group; never place a sleep benefit in a morning alert simply to avoid repetition. Two or three good candidates per pool are enough.                                                                                                                 |
| Frequency                | Rotation changes the body, not the number of reminders. Retain existing prayer/group choices. New categories start off and require explicit selection.                                                                                                                        |
| Extra good-deed messages | Recommend one optional general good-deed message per day at most, at a user-chosen time; none by default. Time-specific reminders have separate switches and visible frequency. Do not silently drop explicitly selected prayer/fasting events to enforce a hidden cap.       |
| Collisions               | Diagnose the duplicate Isha issue first. Suppress duplicate event IDs across applicable instances. Defer/omit optional general content when it would crowd a selected prayer reminder; never postpone a time-critical prayer alert to show a general message.                 |
| Completion               | Keep existing completion-aware routine suppression. A missing app record does not prove the person missed worship. No guilt or streak-pressure wording.                                                                                                                       |
| Quiet hours              | General reminders respect quiet hours. Night worship/suhoor reminders need an explicit wake-at-night choice; turning on general encouragement must not opt someone into overnight alerts.                                                                                     |
| Late delivery            | Do not report a stale lead as the current minutes remaining. Preserve the dated event/absolute time and approve a bounded late-delivery policy; suppress expired pre-Fajr, Duha and fasting-preparation messages.                                                             |
| Equal platforms          | Browser and Android must use the same approved copy/source/route selection. Preserve current honest browser-background and Android approximate-alarm limitations.                                                                                                             |
| Release acceptance       | Exact-text/source snapshots, condition/count tests, deterministic rotation, collision/duplicate tests, timezone/DST/month boundaries, click recovery, cold start and real Android notification screenshots before publication.                                                |

The approved local implementation rotates the ready pools by scheduled civil date. It retains selected event frequency. Prayer titles show the saved clock time to remain truthful after a delayed OS delivery. Browser delivery expires after at most five minutes, with pre-prayer, Friday dua and pre-Fajr boundaries enforced. Android delivery still depends on the OS. Future general/overnight categories retain their explicit opt-in prerequisites.
